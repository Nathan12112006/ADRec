# Redis cache options for AdFlow

Researched 2026-10-07 for [ticket 08](../issues/08-cache-and-failures.md). Official Redis documentation and redis-py API references only. Recommendations below are proposals for the discussion, not accepted decisions or benchmark results.

## Verified mechanisms

- Redis cache-aside checks the cache, loads the primary database on a miss, and populates the cache; writes update the primary and invalidate the cached entity. This permits stale reads and does not make Redis a second source of truth. [Redis cache-aside](https://redis.io/docs/latest/develop/use-cases/cache-aside/)
- `SET key value EX seconds` or `PX milliseconds` installs the value and expiry in one command. Prefer `client.set(key, payload, ex=ttl)` to independent `SET` and `EXPIRE`: failure between separate calls could leave an unexpired entry. `GET` returns nil for an absent key; expired entries become absent on access. Wrong-type values and connection/timeouts are errors, not ordinary misses. [SET](https://redis.io/docs/latest/commands/set/), [GET](https://redis.io/docs/latest/commands/get/), [EXPIRE](https://redis.io/docs/latest/commands/expire/), [redis-py errors](https://redis.io/docs/latest/develop/clients/redis-py/error-handling/)
- redis-py exposes `socket_connect_timeout`, `socket_timeout`, configurable retry/backoff, and pooled connections. The production guide describes automatic retries from version 6 onward. Its stated 10-second timeout defaults conflict with the 5-second defaults in the versioned 8.1 API signatures: explicitly configure these and verify against the pinned version. Socket limits are not a complete wall-clock request deadline; connection establishment, reads, retries, and pool acquisition can add waits. [Production usage](https://redis.io/docs/latest/develop/clients/redis-py/produsage/), [redis-py API](https://redis.readthedocs.io/en/stable/connections.html)
- Reuse connections through a process-lifetime client/pool rather than constructing a client for each request. Async usage explicitly recommends one shared client and closing it at shutdown; the general connection guide supports pooled synchronous use. [Connections](https://redis.io/docs/latest/develop/clients/redis-py/connect/), [Async lifecycle](https://redis.io/docs/latest/develop/clients/redis-py/async/)
- TTL jitter staggers expiry across keys; it does not prevent multiple concurrent misses for one popular key. [Redis on stampedes](https://redis.io/blog/how-to-tame-the-thundering-herd-problem/)
- `maxmemory` and an eviction policy bound cache dataset growth; `allkeys-lru` evicts approximately least-recently-used keys. Redis also supports disabling persistence, appropriate for reconstructible caches. Leave memory headroom beyond `maxmemory` for process overhead. [Eviction](https://redis.io/docs/latest/develop/reference/eviction/), [Persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

## Proposed smallest project contract

Cache only synthetic-user profile fields needed for retrieval/ranking. Keep ad eligibility and current bids, experiment lifecycle/configuration, request outcomes/replays, recommendations, events, and dashboard results in PostgreSQL. A cached user never permits serving without saving the attribution record. Do not initially cache recommendations or experiment results.

Use `adflow:{dataset_version}:profile:v1:{user_id}` and a JSON envelope containing schema version, user ID, and the required typed fields. Validate decoding, schema, and ID match before accepting a hit; malformed entries become an invalid-payload diagnostic and a PostgreSQL reload, with best-effort eviction. Redis strings do not enforce this application schema. Do not negatively cache missing users initially.

Propose configurable 300-second maximum TTL with downward jitter (270–300 seconds), no sliding expiry on hits. On a normal miss, read PostgreSQL and best-effort populate. On Redis read failure, bypass Redis for that request, load PostgreSQL, and skip population. Cache-write failure never turns a completed database-backed operation into a failure. Count usable hits, ordinary misses, invalid payloads, bypasses, and read/write errors separately; define hit ratio over usable hits plus ordinary misses, with other counts displayed alongside it.

For the agreed synchronous backend, reuse a synchronous client/pool in synchronous handlers. Explicitly configure bounded pool size, short connect/read limits, and zero automatic request-path retries (`Retry(NoBackoff(), 0)`). A starting proposal is 100 ms connect and 100 ms socket limits; these are tuning choices, not measured guarantees. Prefer fail-fast pool exhaustion to indefinite blocking. Keep database pool/statement limits separately configured; PostgreSQL failures still return 503 under the established contract.

For disposable local Redis, propose `maxmemory 128mb`, `maxmemory-policy allkeys-lru`, RDB disabled (`save ""`), and `appendonly no`. Restarting Redis causes cold misses and repopulation. No distributed locks, replicas, or persistence are needed initially; concurrent misses may perform duplicate reads and must be measured before adding coordination.

## Consistency boundary and tests

Application-managed profile updates should commit PostgreSQL first, then best-effort `DEL`. **Inference from cache-aside ordering:** a reader can load the old row, an updater can commit and delete, then the reader can populate the old row afterward. Therefore invalidation plus TTL is eventual consistency. TTL bounds residence after cache population, not an absolute freshness interval measured from a database update; delayed reads/fills add age. See [Redis consistency discussion](https://redis.io/blog/cache-consistency-strategies/).

Ask whether this tolerance is acceptable for synthetic profiles. Avoid promising strict freshness without version-aware fills or stronger coordination. Pause traffic and change the dataset namespace across all processes on reseeding/replacement; old keys then expire unused. Out-of-band SQL profile changes require explicit invalidation/namespace change or acceptance of stale cached values. Defer live profile-edit APIs if they add no demo value.

Focused checks: hit/miss and expiry; malformed/schema-mismatched JSON; unknown user; read timeout/disconnection and pool exhaustion; write failure after a successful DB read; restart/eviction cold recovery; duplicate concurrent misses; commit/invalidation race; namespace isolation. Verify database/event invariants survive Redis failure and that no cache speedup is claimed without measurements.
